# CoView（废弃）

CoView 是一个 0 成本取向的临时共同观影网页项目。用户无需注册登录，先选择房主或房客身份，再创建或加入临时房间。房主填写视频页面或视频资源地址，后端自动判断使用同步播放模式还是屏幕共享模式。

## 项目状态

本项目目前已废弃。经过实践和复盘后，我认为它已经没有继续投入的价值，也偏离了最初“轻便、简单、像一个带聊天框的遥控器一样协助双方共同观影”的设想。

项目最初希望直接对双方的视频页面进行操作和同步控制，但在实现过程中发现，这个核心设想会受到浏览器安全机制和用户隐私保护限制的约束。现代浏览器不会允许普通网页随意读取、控制或远程操作另一个第三方视频页面，这一点使得“直接操控视频页面”这个根本能力无法可靠实现。

为绕过这个核心限制，项目后续尝试引入同步播放和屏幕共享两套方案：能直连的视频资源走同步播放，受限平台页面则走屏幕共享。从结果上看，这套方案确实能在一定程度上完成共同观影，但实现复杂度明显上升，用户操作链路变长，工程结构也越来越重，最终违背了项目最初追求方便、轻量、简洁的目标。

## 废弃原因

- 核心价值不再成立：项目的最终形态已经不像最初设想中的“轻便遥控器”，而更像一个复杂的观影协同系统。
- 浏览器限制不可忽略：安全策略和隐私保护机制限制了网页对第三方视频页面的直接操控能力。
- 方案复杂度过高：同步播放、屏幕共享、WebRTC 信令、裁剪共享、房主管理台等功能叠加后，维护和使用成本都明显增加。
- 用户体验偏离初衷：为了兼容不同视频来源，用户需要理解房主、房客、同步播放、屏幕共享、裁剪区域、播放申请等概念，已经不够直观。
- 投屏选画面无法自动化：虽然开发者模式下可以人工查看前端界面分布，但“用户自己查看”和“网页代码读取另一个页面的界面信息”是两回事。出于隐私与安全限制，代码无法直接获取第三方视频页面的结构、位置和可共享区域，只能让用户通过截屏和手动裁剪绕开。
- 截屏裁剪体验不稳定：当用户切换全屏、页面布局变化或重新选择窗口时，往往需要再次截屏和调整裁剪区域，实际使用并不方便。
- 屏幕共享存在隐私风险：录屏或共享窗口时，用户弹出的消息、账号信息、通知等隐私内容可能被一并公开，项目本身无法从根本上规避这类风险。
- 置顶/PiP 弹窗能力受限：浏览器提供的置顶管理台或画中画窗口并不是完全自由的 UI 容器，大小、形状、样式和透明效果都会受到浏览器限制，无法完全做成最初设想中对应大小、形状和半透明效果的悬浮按钮。
- 继续优化价值不足：在复杂度上升后，项目没有形成足够清晰、稳定、低门槛的使用价值，也缺少继续优化推进的必要性。
- 工程评估不足：早期对浏览器权限边界、隐私限制、不同视频平台限制和整体技术风险的判断不够全面。

## 项目收获

- 更深入理解了浏览器安全模型和隐私保护边界，尤其是网页无法随意控制第三方页面、媒体播放和用户屏幕内容这一类限制。
- 提升了项目价值评估经验：技术上可行不代表实用性上值得做，能绕过问题也不代表方案足够简单、可靠、可实用。
- 认识到 MVP 应该更严格地守住核心假设，早期就要验证最关键、最不可替代的能力是否真实可行。
- 对工程复杂度有了更直观的感受：当一个轻量想法需要多套兜底方案才能成立时，就需要重新评估它是否还符合最初目标。
- 理解了“人工可见”和“代码可读取”之间的边界：开发者工具能看到页面结构，并不代表业务代码有权限读取、定位或控制另一个页面。
- 更清楚地认识到屏幕共享类功能的隐私风险：即使功能可以实现，也需要评估用户通知、账号信息、聊天消息等意外暴露的可能性。
- 认识到用户手动截屏、裁剪、重新选择窗口这类流程会显著增加使用成本，技术兜底方案如果依赖频繁人工操作，就很难保持产品轻便。
- 实践中了解了浏览器置顶窗口、弹窗和 PiP 类能力的实际限制，包括窗口样式、透明度、尺寸形态和可控范围并不能完全按产品想法设计。
- 尝试并实践了新的技术栈，包括 Spring Boot 3.3.5、Spring MVC、Spring WebSocket、Bean Validation、React 18 UMD、Hls.js，以及基于公开 STUN 的 WebRTC 浏览器点对点连接。
- 积累了前后端实时协作场景的经验，包括 REST API、WebSocket 状态同步、WebRTC 信令转发、房间状态管理、临时身份管理和内存数据生命周期处理。

## 当前功能

- 房主创建临时房间，房间号固定为 `LJX-` 前缀加 6 位字母数字，例如 `LJX-a1B2c3`。
- 房主创建房间时必须设置密码并二次确认，房客加入时需要输入房间号和密码。
- 房客提交加入申请后，房主同意才会生成正式成员身份并进入房间。
- 后端会从复制的分享文案中提取第一个网址，再判定播放模式。
- 同步播放模式支持 `.mp4`、`.webm`、`.m3u8` 等浏览器可直接播放的资源。
- 屏幕共享模式用于腾讯视频、抖音、B 站、爱奇艺、YouTube 等不适合直接嵌入或控制的平台页面。
- 房主可打开浏览器原生置顶管理台，处理加入申请、聊天、成员状态、播放申请和视频来源更换。
- 房间内支持文字聊天，消息通过 WebSocket 实时广播。
- 房客可以向房主申请播放、暂停、进度跳转、开弹幕和关弹幕。
- 房客退出时只移除自身成员，房主退出时关闭整个临时房间。

## 技术栈

- 后端：Java 17、Spring Boot 3.3.5、Spring MVC、Spring WebSocket、Bean Validation
- 前端：静态 HTML + React 18 UMD + Hls.js，由 Spring Boot 直接托管
- 实时通信：WebSocket 负责状态同步、聊天和 WebRTC 信令
- 实时媒体：WebRTC 浏览器点对点连接，默认使用公开 STUN
- 数据：内存临时存储，不依赖数据库
- 测试：JUnit 5、Spring Boot Test

前端运行时会从 CDN 加载 React、ReactDOM 和 Hls.js，相关引用在 `src/main/resources/static/index.html` 中。

## 本地运行

需要 Java 17 和 Maven。

```bash
mvn spring-boot:run
```

打开：

```text
http://localhost:8080
```

运行测试：

```bash
   mvn test
```

打包：

```bash
   mvn clean package
   java -jar target/CoView-1.0-SNAPSHOT.jar
```

Docker 构建示例：

```bash
   docker build -t coview .
   docker run --rm -p 8080:8080 coview
```

服务端口默认读取环境变量 `PORT`，未设置时使用 `8080`。

## 使用流程

1. 房主进入首页，选择“我是房主”。
2. 填写昵称、视频页面或资源地址，设置并确认房间密码。
3. 系统生成候选房间号，房主点击创建后房间号才正式生效。
4. 房客选择“我是房客”，输入房间号和密码，提交加入申请。
5. 房主在房间页或房主管理台同意申请。
6. 后端根据来源进入同步播放或屏幕共享流程。

## REST API

- `GET /api/health`：健康检查
- `GET /api/rooms/candidate-id`：生成一个尚未生效的候选房间号
- `POST /api/rooms`：创建房间并返回房主会话
- `GET /api/rooms/{roomId}`：读取房间快照
- `POST /api/rooms/{roomId}/join-requests`：房客提交加入申请
- `GET /api/rooms/{roomId}/join-requests?participantId=...`：房主读取待确认申请
- `GET /api/rooms/{roomId}/join-requests/{requestId}`：房客轮询申请状态
- `POST /api/rooms/{roomId}/join-requests/{requestId}/decision`：房主同意或拒绝加入申请
- `PUT /api/rooms/{roomId}/source`：房主更换视频来源

## WebSocket

连接地址：

```text
WS /ws/rooms/{roomId}?participantId=...
```

主要消息类型：

- `snapshot`：后端发送房间完整快照
- `presence`：成员加入、离开或连接变化后的房间状态
- `playback`：房主广播播放、暂停、进度或状态同步
- `playback-request`：房客向房主申请播放相关操作
- `playback-request-decision`：房主处理房客播放申请后的通知
- `screen-share`：房主屏幕共享开关状态
- `webrtc-signal`：WebRTC offer、answer、candidate 信令转发
- `chat`：房间聊天消息
- `leave`：成员主动退出
- `room-refresh`：请求广播最新房间快照
- `ping`/`pong`：连接保活

## 播放模式

同步播放模式：

- 适合浏览器能直接加载的视频资源。
- 每个成员直接从原始 URL 播放视频。
- 服务端只同步播放状态，不转发视频内容。

屏幕共享模式：

- 适合第三方视频网站页面或无法稳定直连的视频地址。
- 房主在原网页正常播放，通过浏览器屏幕共享采集画面和声音。
- 前端会先截取画面供房主选择裁剪区域，再通过 WebRTC 点对点发送给房客。

## 数据生命周期

- 房间、成员、密码摘要、加入申请和播放状态都保存在当前 Java 进程内存中。
- 房间 12 小时无活动后由定时任务清理。
- 重启服务会清空所有房间。
- 密码以 SHA-256 摘要形式保存在内存中，不落盘。

## 当前边界

CoView 不提供影视资源，不缓存媒体文件，不下载、不转码、不代理第三方视频，也不绕过第三方平台限制。受限平台页面使用屏幕共享，由房主在原网站正常播放。

WebRTC 当前只配置公开 STUN，没有 TURN 中继。大多数普通网络可以尝试直连；如果双方处于严格 NAT 或企业网络，连接可能失败。稳定商用通常需要 TURN 服务、持久化存储、权限体系和更完整的部署监控。
